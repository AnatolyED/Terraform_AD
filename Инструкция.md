# Инструкция

Поднимаем одну новую Debian 12 VM для GitLab Runner. Действующие Windows AD, Vault и корпоративный GitLab используем по их DNS-именам. Terraform запускается в Docker на Runner.

На GitHub исходный код находится в ветке `feature/ad-password-bootstrap` с пустым инвентарём production. В корпоративном GitLab опубликуйте его как `main`. В командах замените значения в `<…>` на реальные. Пароли, PEM, токены и локальные параметры храните вне репозитория.

## 1. Подготовить доступы

| Что понадобится | Где взять |
| --- | --- |
| URL GitLab, право создать закрытый проект, доступ к state | Администратор GitLab; для текущей матрицы нужен GitLab 18.6+ с поддержкой matrix expressions |
| LDAPS URL, PEM CA AD, DN выделенной OU | Администратор AD; делегируйте управление этой OU учётке Terraform |
| HTTPS URL и PEM CA каждого Vault, операторский доступ | Администратор Vault; уточните версию, namespace и занятые пути `gitlab-jwt/`, `ad-ldap/` и `ad-creds/` |
| Две bind-учётки Vault | AD-учётка для чтения пользователей и групп и отдельная учётка для Reset Password только у целевых сервисных записей |
| Пакеты Docker и образы | Разрешённый APT и Docker Registry либо проверенные архивы |

Проверьте DNS и маршруты. Runner и его job-контейнеры должны видеть GitLab по HTTPS, AD по LDAPS и Vault по HTTPS. Vault должен видеть AD по LDAPS и GitLab по HTTPS для проверки JWT. Сверьте версии действующих Vault с нужными возможностями LDAP auth, LDAP secrets engine и JWT. Стенд проверялся с Vault 2.2.1. [Матрица GitLab](https://docs.gitlab.com/ci/yaml/matrix_expressions/) · [LDAP secrets engine](https://developer.hashicorp.com/vault/docs/secrets/ldap)

## 2. Подготовить чистую Debian VM

На Debian установите базовые пакеты.

```bash
sudo apt update
sudo apt install -y git curl ca-certificates jq ldap-utils
```

Если корпоративный APT уже отдаёт Docker Engine, переходите к установке. Иначе с разрешения администратора добавьте официальный источник. Для разрешённого зеркала замените `docker_apt` на `https://mirror.yandex.ru/mirrors/download.docker.com/linux/debian`.

```bash
docker_apt=https://download.docker.com/linux/debian
sudo install -d -m 0755 /etc/apt/keyrings
sudo curl -fsSL "$docker_apt/gpg" -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc
printf 'deb [arch=amd64 signed-by=/etc/apt/keyrings/docker.asc] %s bookworm stable\n' "$docker_apt" |
  sudo tee /etc/apt/sources.list.d/docker.list >/dev/null
sudo apt update
```

Установите и запустите Docker.

```bash
sudo apt install -y docker-ce docker-ce-cli containerd.io
sudo systemctl enable --now docker
sudo docker version
```

При закрытом доступе используйте утверждённый репозиторий или `sudo apt install /путь/к/пакетам/*.deb` с комплектом зависимостей Debian 12. [Установка Docker на Debian](https://docs.docker.com/engine/install/debian/)

При корпоративном CA установите доверенный PEM GitLab в Debian и проверьте URL.

```bash
sudo install -m 0644 "$HOME/gitlab-ca.pem" /usr/local/share/ca-certificates/corp-gitlab.crt
sudo update-ca-certificates
curl -fsS 'https://<GITLAB_FQDN>/.well-known/openid-configuration'
```

## 3. Создать проект в корпоративном GitLab

Создайте пустой **Private** проект без стартового README. Убедитесь, что администратор включил Terraform state на сервере, а в проекте доступен раздел **Operate → Terraform states**. [GitLab-managed state](https://docs.gitlab.com/user/infrastructure/iac/terraform_state/)

```bash
git clone --single-branch -b feature/ad-password-bootstrap https://github.com/AnatolyED/Terraform_AD.git
cd Terraform_AD
git branch -m main
git remote rename origin github
git remote add origin 'https://<GITLAB_FQDN>/<GROUP>/<PROJECT>.git'
git push -u -o ci.skip origin main
```

Если Debian не имеет доступа к GitHub, клонируйте ветку на доступном ПК и перенесите рабочую копию вместе с каталогом `.git`. На Debian продолжите с `git branch -m main`.

Назначьте `main` веткой по умолчанию и защитите её. Дальнейшие правки делайте через MR. Запишите числовой **Project ID** из **Settings → General**.

## 4. Подключить два Runner

Если в проекте уже есть два онлайн Runner с нужными тегами и доступом к сервисам, переходите к шагу 5.

В **Settings → CI/CD → Runners** создайте два проектных Runner. Первый с тегом `terraform-docker`, второй с тегом `terraform-deploy` и флагом **Protected**. Для обоих выключите **Run untagged**. GitLab выдаст отдельный токен `glrt-…` для каждой регистрации. [Регистрация Runner](https://docs.gitlab.com/runner/register/)

Подберите версию Runner под корпоративный GitLab. Загрузите на VM образ Runner, helper той же версии для AMD64 и образ Terraform 1.17.1. Используйте разрешённый реестр или `sudo docker load -i runner-images.tar` для проверенного архива. Ниже приведено имя образа из нашего архива. Для другого реестра или версии подставьте точное имя загруженного образа.

```bash
runner_image='terraform-ad/runner:19.5.1'
sudo install -d -m 0700 /srv/terraform-ad-runner
sudo docker run -d --name terraform-ad-runner --restart unless-stopped --pull never \
  -v /srv/terraform-ad-runner:/etc/gitlab-runner \
  -v /var/run/docker.sock:/var/run/docker.sock "$runner_image"
```

При частном CA перед регистрацией выполните `sudo install -m 0644 "$HOME/gitlab-ca.pem" /srv/terraform-ad-runner/gitlab-ca.pem`.

Запустите регистрацию дважды. Каждый раз введите URL GitLab, токен соответствующего Runner, имя и executor `docker`. На запрос образа укажите тот же образ Terraform, который будете использовать в CI. Для GitLab с публичным CA опустите аргумент `--tls-ca-file`.

```bash
sudo docker exec -it terraform-ad-runner gitlab-runner register \
  --tls-ca-file /etc/gitlab-runner/gitlab-ca.pem
```

Откройте `sudoedit /srv/terraform-ad-runner/config.toml`. В существующих секциях `[runners.docker]` обоих Runner оставьте `privileged = false` и задайте `pull_policy = ["if-not-present"]`. Если используете helper из нашего архива, добавьте `helper_image = "terraform-ad/runner-helper:19.5.1"`. Для другого локального helper подставьте его имя. Используйте VM для задач доверенного проекта.

```bash
sudo docker restart terraform-ad-runner
sudo docker exec terraform-ad-runner gitlab-runner verify
```

Ожидаются две успешные проверки и два Runner онлайн. Созданный при регистрации `config.toml` содержит токены и остаётся на VM.

Перед первым запуском AD соберите на каждом deploy Runner образ с утилитой Go. Если Terraform загружен под локальным тегом, передайте этот тег через `--build-arg TERRAFORM_IMAGE=terraform-ad/terraform:1.17.1`. Для сборки через корпоративный реестр передайте образ компилятора через `--build-arg GO_IMAGE=…`. В закрытую сеть можно перенести готовый образ через `docker save` и `docker load`. При публикации образа в корпоративном реестре задайте `AD_DEPLOY_IMAGE` с его полным именем.

```bash
sudo docker build -f config/ad-deploy.Dockerfile \
  -t terraform-ad/terraform-ad-deploy:1.17.1-go .
```

## 5. Запустить validate и заполнить инвентарь

В **Build → Pipelines → New pipeline** выберите `main` и запустите первый столбец. Если образ Terraform загружен как `terraform-ad/terraform:1.17.1`, укажите это имя в `TERRAFORM_IMAGE`.

| Переменная | Validate | AD | Первый Vault |
| --- | --- | --- | --- |
| `TERRAFORM_SOURCE` | `upstream` | то же | то же |
| `TERRAFORM_IMAGE` | Точное имя локального или разрешённого образа | то же | то же |
| `AD_DEPLOY_ENVIRONMENT` | `production` | то же | то же |
| `AD_DEPLOY_ENABLED` | `false` | `true` | `false` |
| `VAULT_DEPLOY_MODE` | `off` | `off` | `single` |
| `VAULT_TARGET_ID` | пусто | пусто | `vault-01` |

При `upstream` Runner скачивает официальный Vault provider из реестра Terraform, исправленный AD provider — из GitHub Release. При ограничениях используйте доступное зеркало для Vault с `TERRAFORM_SOURCE=yandex`, при необходимости заменив URL в `config/terraform.yandex.tfrc` на корпоративное зеркало с поддержкой протокола Terraform. Для копии закреплённого ZIP AD задайте `AD_PROVIDER_RELEASE_URL` с HTTPS-адресом. Контрольные суммы и lock-файлы сохраняются.

После двух зелёных `validate` заполните инвентарь в отдельной ветке и откройте MR.

| Файл | Что заполнить |
| --- | --- |
| `data/active-directory/production/ou.yaml` | Ключи OU, `name` и при необходимости `parent_id` |
| `data/active-directory/production/users.yaml` | Ключи записей, `name`, `sam_account_name`, `principal_name`, `ou_id` и параметры учётки |
| `data/active-directory/production/groups.yaml` | Ключи групп, `name`, `sam_account_name`, `ou_id` и при необходимости `membership` |
| `data/vault/clusters.yaml` | Ключ кластера, HTTPS URL, `ad_environment: production`, версии bind-паролей, политики и роли |

Начните с одного кластера `vault-01`. Поле `membership` задаёт полный состав выбранной группы. Для ротации используйте отдельную сервисную учётку на каждую роль. Примеры полей есть в [схеме YAML](https://github.com/AnatolyED/Terraform_AD/blob/e11f3e227514c2910ea2123075ed27790fbaf25f/docs/configuration.md#1-сущности-инвентаря).

## 6. Подключить AD и проверить план

В **Settings → CI/CD → Variables** задайте scope `ad/production`. Для всех строк включите **Protected** и выключите **Expand variable reference**. Пароли — **Masked and hidden**, PEM — **File**.

| Ключ | Что вставить |
| --- | --- |
| `AD_USERNAME` и `AD_PASSWORD` | UPN и пароль делегированной учётки Terraform |
| `AD_TLS_CA_CERT_FILE` | PEM цепочки CA AD |
| `TF_VAR_ad_ldap_url` | `ldaps://<DC_FQDN>:636` |
| `TF_VAR_ad_managed_base_dn` | DN существующей выделенной OU |
| `AD_BOOTSTRAP_VAULT_ADDR` | HTTPS-адрес выбранного Vault. Используйте адрес, через который запросы обслуживает активный узел |
| `AD_BOOTSTRAP_VAULT_CACERT` | PEM цепочки CA этого Vault, тип **File** |
| `AD_BOOTSTRAP_VAULT_NAMESPACE` | Namespace в Vault Enterprise, если используется |
| `TF_VAR_ad_user_passwords` | Необязательная JSON-карта для явной смены пароля через `password_version` или отдельного ручного назначения |

### Один раз настроить Vault для начальных паролей

Выберите один Vault для начальных паролей AD. Заполните на административной машине `VAULT_ADDR`, `VAULT_CACERT` и при необходимости `VAULT_NAMESPACE`. Используйте административную сессию Vault и подготовьте JWT mount `gitlab-jwt/` по первым командам шага 7. Роли из шага 7 для `vault:plan` и `vault:apply` нужны отдельно при включении управления самим Vault.

```bash
sh config/configure-ad-password-bootstrap.sh 'https://<GITLAB_FQDN>' '<PROJECT_ID>' main production
```

Скрипт готовит KV v2 и роли для указанного проекта, защищённой ветки и окружения. Он использует отдельный путь `ad-bootstrap/projects/<PROJECT_ID>/production/<ключ из users.yaml>`. Для выдачи начального пароля оператору делегируйте чтение конкретного пути, не выдавая доступ ко всему mount. В UI откройте **Secrets → ad-bootstrap → projects → <PROJECT_ID> → production → <ключ пользователя>**. Используйте его для первичной выдачи. Для личных учёток задавайте `change_password_at_logon: true`. Для сервисных учёток с ротацией используйте актуальные данные из `ad-creds`.

Чтобы добавить несколько пользователей, внесите их в один MR. Для каждой новой активной учётки `ad:plan` создаёт секрет в Vault, если его ещё нет. Ручной `ad:apply` получает первую версию секрета. В артефакте сохраняются ключи записей и путь проекта, а значение пароля проходит через эфемерную переменную Terraform. Существующие записи определяются по state. Если запись уже есть в AD, импортируйте её. Если предыдущий apply изменил state, запустите новый план. После применения повторите пайплайн и проверьте, что `ad:plan` показывает `No changes` и `AD initial passwords loaded from Vault: 0`.

### Проверить AD и запустить план

Проверьте делегированную учётку с VM. Впишите её UPN и используйте пароль по запросу.

```bash
LDAPTLS_CACERT="$HOME/ad-ca.pem" ldapwhoami -x -H 'ldaps://<DC_FQDN>:636' -D '<BIND_UPN>' -W
```

State AD называется `ad-production`. Если объекты уже под Terraform, сначала сохраните резервную копию, перенесите существующий state и проверьте адреса ресурсов. Существующие объекты вне Terraform импортируйте по GUID. Для первого импорта можно добавить в MR файл `infra/active-directory/imports.tf` и проверить запланированный импорт в CI.

```hcl
import {
  to = module.directory.ad_ou.top_level["<КЛЮЧ_ИЗ_OU_YAML>"]
  id = "<OBJECT_GUID>"
}
```

Запустите столбец **AD**, откройте `ad:plan`. Сверьте все создания, импорты, изменения членства и возможные удаления. При неожиданном изменении остановитесь. Ручной `ad:apply` запускайте после проверки и согласования.

## 7. Подключить GitLab к первому Vault

Работайте с Vault CLI на администраторской машине из корня репозитория. Поместите PEM CA GitLab в `~/gitlab-ca.pem`, а PEM CA этого Vault в `~/vault-ca.pem`. При использовании Enterprise namespace задайте `VAULT_NAMESPACE` и на машине, и для задания GitLab.

```bash
gitlab='https://<GITLAB_FQDN>'
export VAULT_ADDR='https://<VAULT_FQDN>:8200'
export VAULT_CACERT="$HOME/vault-ca.pem"
issuer=$(curl -fsS --cacert "$HOME/gitlab-ca.pem" "$gitlab/.well-known/openid-configuration" | jq -er .issuer)
printf '%s\n' "$issuer"
read -rsp 'Операторский токен Vault: ' VAULT_TOKEN
printf '\n'
export VAULT_TOKEN
vault auth list
```

Проверьте, что issuer соответствует корпоративному GitLab. Если `gitlab-jwt/` свободен, выполните первые две команды. Для существующего mount сверьте `vault read auth/gitlab-jwt/config` и убедитесь, что роли и политики ниже выделены этому проекту. При совпадении имён с чужим проектом согласуйте отдельные имена и адаптацию CI до записи.

```bash
vault auth enable -path=gitlab-jwt jwt
vault write auth/gitlab-jwt/config oidc_discovery_url="$gitlab" bound_issuer="$issuer" oidc_discovery_ca_pem=@"$HOME/gitlab-ca.pem"
vault policy write terraform-ad-plan config/vault/terraform-plan.hcl
vault policy write terraform-ad-apply config/vault/terraform-apply.hcl
```

Создайте `~/vault-plan.json` с содержимым ниже. Подставьте внешний URL GitLab без завершающего слеша, числовой ID проекта в кавычках и ID кластера. GitLab будет выдавать заданиям временные JWT. [Vault JWT](https://developer.hashicorp.com/vault/docs/auth/jwt) · [GitLab ID tokens](https://docs.gitlab.com/ci/secrets/id_token_authentication/)

```json
{
  "role_type": "jwt",
  "user_claim": "sub",
  "bound_audiences": ["<GITLAB_URL>/terraform/vault/plan"],
  "bound_claims": {
    "project_id": "<PROJECT_ID>",
    "ref_type": "branch",
    "ref": "main",
    "ref_protected": "true",
    "environment": "vault/<VAULT_ID>",
    "environment_action": "verify"
  },
  "token_policies": ["terraform-ad-plan"],
  "token_explicit_max_ttl": 900
}
```

Создайте `~/vault-apply.json` как копию `~/vault-plan.json` и измените три поля.

| Поле | Значение для apply |
| --- | --- |
| `bound_audiences` | `["<GITLAB_URL>/terraform/vault/apply"]` |
| `bound_claims.environment_action` | `"start"` |
| `token_policies` | `["terraform-ad-plan", "terraform-ad-apply"]` |

```bash
vault write auth/gitlab-jwt/role/terraform-plan @"$HOME/vault-plan.json"
vault write auth/gitlab-jwt/role/terraform-apply @"$HOME/vault-apply.json"
unset VAULT_TOKEN
```

## 8. Проверить план первого Vault и подключить остальные

Добавьте переменные GitLab со scope `vault/vault-01`. Используйте **Protected**, **File** для PEM и **Masked and hidden** для паролей.

| Ключ | Что вставить |
| --- | --- |
| `VAULT_CACERT`, `TF_VAR_vault_ldap_ca_file` | PEM CA Vault и AD, два отдельных файла |
| `TF_VAR_vault_ldap_url` | LDAPS URL контроллера AD |
| `TF_VAR_vault_ldap_auth_bind_dn`, `TF_VAR_vault_ldap_auth_bind_password` | DN и пароль учётки LDAP-чтения |
| `TF_VAR_vault_ldap_auth_user_dn`, `TF_VAR_vault_ldap_auth_group_dn` | DN баз поиска пользователей и групп |
| `TF_VAR_vault_ldap_secrets_bind_dn`, `TF_VAR_vault_ldap_secrets_bind_password` | DN и пароль отдельной учётки ротации |
| `TF_VAR_vault_ldap_secrets_user_dn` | DN базы поиска сервисных записей |

Сверьте существующие mount, политики и роли этого Vault. Если объект уже под Terraform, перенесите его state. Для существующего объекта вне Terraform можно использовать `infra/vault/imports.tf` и проверить импорт в плане `vault-vault-01`. Для провайдера Vault 5.13.0 используйте ID `ad-creds`: добавление `/config` приводит к запросу `ad-creds/config/config`.

```hcl
import {
  to = vault_ldap_auth_backend.directory
  id = "ad-ldap"
}

import {
  to = vault_ldap_secret_backend.directory
  id = "ad-creds"
}
```

Импорт LDAP mount может показать обновление write-only bind-пароля. Проверьте фактический пароль и согласуйте это изменение до применения. При импорте существующей статической LDAP-роли провайдер 5.13.0 может предложить замену из-за отсутствующего `role_name` в импортированном state. Защита `prevent_destroy` останавливает такой план. Для первого плана с новым state исключите эту существующую роль из `static_roles` и файла импорта, затем решите её перенос отдельно. При наличии state, в котором роль уже управляется, сначала проверьте его перенос.

Запустите столбец **Первый Vault**, проверьте `vault:plan` и вручную запустите `vault:apply` в согласованное окно. Первая настройка статической роли может сразу сменить пароль сервисной записи, поэтому сначала подготовьте потребителя секрета.

Проверьте вход через LDAP, доступ читателя, отказ пользователю вне группы и вход сервисной записи с новым паролем после ротации. Повторите план и проверьте `No changes`. После успешного импорта удалите временный `imports.tf` Vault через MR перед включением следующего кластера. Добавьте ID следующего Vault в YAML и матрицу CI, повторите шаги 7–8 с отдельным scope и state. Подключайте кластеры по одному через режим `single`.
